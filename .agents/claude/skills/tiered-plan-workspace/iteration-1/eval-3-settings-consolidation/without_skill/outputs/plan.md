# Plan: Consolidate per-environment JSON settings into a single TOML file

**Mode:** solo developer, one release for backwards-compat, one PR (probably split into a few commits).

---

## 1. Goal and shape of the change

Replace `config/dev.json`, `config/staging.json`, `config/prod.json` with a single `config/settings.toml` that has one `[env.<name>]` section per environment, plus an optional `[default]` section for shared keys.

Deliverables:

1. A new `settings.toml` (committed) generated from the current JSONs.
2. A loader that prefers TOML, falls back to the legacy JSONs with a deprecation warning, and merges `[default]` under each env.
3. A one-shot migration script that produces `settings.toml` from the existing JSONs (idempotent, runnable by any future contributor on a fork).
4. A CLI flag `--dump-config` (and `--dump-config-format=toml|json`) that prints the fully merged, effective config for the selected environment to stdout, then exits 0.
5. One release cycle of dual-read, then removal of the JSON path in the *next* release.

Non-goals:

- No change to which keys exist or what they mean.
- No secrets management overhaul. If a key was a secret in JSON, it stays a secret in TOML (same `.gitignore` posture).
- No runtime hot-reload.

---

## 2. Target file layout

```
config/
  settings.toml          # new, committed
  dev.json               # kept for one release, will be deleted next release
  staging.json
  prod.json
scripts/
  migrate_settings.py    # one-shot JSON -> TOML generator
src/<pkg>/config/
  __init__.py
  loader.py              # new: load_settings(env) -> dict
  legacy_json.py         # new: thin wrapper around old per-env JSON read, emits DeprecationWarning
  cli.py                 # extended: --dump-config, --dump-config-format
tests/config/
  test_loader.py
  test_legacy_fallback.py
  test_dump_cli.py
  fixtures/
    settings.toml
    dev.json
    staging.json
    prod.json
```

`settings.toml` shape:

```toml
[default]
log_level = "INFO"
timeout_seconds = 30

[env.dev]
database_url = "postgres://localhost/app_dev"
debug = true

[env.staging]
database_url = "postgres://staging.internal/app"
debug = false

[env.prod]
database_url = "postgres://prod.internal/app"
log_level = "WARNING"   # overrides [default]
debug = false
```

Merge rule: `effective = deep_merge(default, env.<name>)`, env wins on conflict.

## 3. Sequence of work (commit-sized chunks)

### Commit 1 - Loader + tests, no migration yet

- Add `src/<pkg>/config/loader.py` with `load_settings(env: str, *, config_dir: Path | None = None) -> dict`.
- Behavior: if `<config_dir>/settings.toml` exists -> read it, deep-merge `[default]` with `[env.<env>]`, return.
- If not, fall back to `<config_dir>/<env>.json`, emit `DeprecationWarning` (and a `logging.warning` so it shows in prod logs that filter `warnings`).
- If neither exists -> raise `ConfigNotFoundError` with both paths it tried.
- Use `tomllib` (stdlib, Python 3.11+). If the project supports <3.11, depend on `tomli`. Decide based on `pyproject.toml`'s python requirement — record the choice in the commit message.
- Tests:
  - TOML-only present: correct merge, default overridden by env.
  - JSON-only present: returns same dict the old code would have, and a `DeprecationWarning` is emitted (use `pytest.warns`).
  - Both present: TOML wins, no warning emitted.
  - Neither present: `ConfigNotFoundError`.
  - Unknown env name: explicit error listing available envs.

Acceptance: tests green. Old callers untouched.

### Commit 2 - Wire the loader into the app

- Replace existing call sites that did `json.load(open("config/<env>.json"))` with `load_settings(env)`.
- Grep for `config/` string literals and `.json` reads under `config/` to make sure none are missed.
- No behavior change expected for users still on JSONs.

Acceptance: app boots in all three envs against the JSON files via the new loader (legacy path), deprecation warning visible in logs.

### Commit 3 - Migration script + generated `settings.toml`

- Add `scripts/migrate_settings.py`:
  - Reads all `config/*.json`, builds a single TOML doc.
  - Promotes keys with identical values across **all** envs into `[default]` (configurable via `--no-promote` flag; default is to promote, since the user explicitly wants consolidation).
  - Writes to `config/settings.toml`. Refuses to overwrite unless `--force`.
  - Idempotent: running twice produces the same file (sorted keys, stable section order: `default`, then envs alphabetical).
- Run it once locally, commit the resulting `config/settings.toml`.
- Add a short note at the top of the generated TOML: `# Generated by scripts/migrate_settings.py on <date>. Edit by hand thereafter.`

Acceptance: `load_settings("dev")` from TOML returns a dict equal to `load_settings("dev")` from JSON (asserted by a test that uses the fixture pair). Same for staging, prod.

### Commit 4 - `--dump-config` CLI flag

- Extend the existing CLI entry point. Two flags:
  - `--dump-config`: print merged effective config for the resolved environment, exit 0.
  - `--dump-config-format {toml,json}`: defaults to `toml`. JSON output is pretty-printed (`indent=2`, sorted keys).
- The env is resolved by the same mechanism the app already uses (env var, `--env` flag, whatever exists). Document that in `--help`.
- Redact: if there's an existing convention for marking secret keys (e.g. names ending in `_SECRET`, `_TOKEN`, `_PASSWORD`), replace their values with `"***"` in the dump. If no such convention exists, dump everything raw and note in `--help` that the output may contain secrets. (Solo project — pick one, write it down in `STATE.md`.)
- Tests:
  - `--dump-config` with TOML present prints merged config.
  - `--dump-config-format=json` prints valid JSON parseable back to the same dict.
  - Exit code 0; no extra log lines on stdout (warnings go to stderr).

Acceptance: `python -m <pkg> --env=prod --dump-config` shows the prod-effective config and nothing else on stdout.

### Commit 5 - Docs + deprecation notice

- Update `README.md` (or wherever config is documented) with the new TOML format and a short migration paragraph: "Old `config/<env>.json` files are still read for one release. Run `python scripts/migrate_settings.py` to generate `settings.toml`, then delete the JSONs."
- Add `CHANGELOG.md` entry under "Deprecated": "Per-environment JSON config files. Will be removed in the next release. Use `config/settings.toml`."
- Bump version per project's convention.

Acceptance: a fresh reader of the README can set up a new env without seeing the JSONs.

### Next release (out of scope for this PR, tracked in STATE.md)

- Delete `config/*.json`.
- Delete `legacy_json.py` and the fallback branch in `loader.py`.
- Drop `DeprecationWarning`.
- Tests for the legacy fallback get deleted with it.

## 4. Design decisions worth pinning now

| Decision | Choice | Why |
|---|---|---|
| TOML parser | `tomllib` if py>=3.11, else `tomli` | stdlib preferred; only add a dep if forced |
| TOML writer | `tomli-w` | `tomllib` is read-only; `tomli-w` is the standard companion |
| Merge semantics | Deep merge, env-over-default | matches `[default]` intent; one rule, easy to explain |
| Lists | Replace, do not concatenate | concatenation surprises people; document this |
| Unknown env | Hard error listing valid envs | silent fallback to `dev` masks deploy bugs |
| Warning channel | `warnings.warn(DeprecationWarning)` + `logging.warning` | one for devs running tests, one for ops reading logs |
| Secret redaction in dump | Suffix-based heuristic, documented | good enough for solo; revisit if a real secrets system lands |

## 5. Risks and how this plan addresses them

- **Risk: TOML drift from JSON during migration.** Mitigation: commit 3 includes a test that loads each JSON and the migrated TOML and asserts dict equality. That test stays green for the dual-read release, then gets deleted with the JSONs.
- **Risk: Someone edits a JSON after `settings.toml` lands and is confused when their change is ignored.** Mitigation: when TOML is present and JSONs are also present, emit a `logging.warning` per env JSON file found: "Ignoring config/dev.json — settings.toml is the source of truth. Delete the JSON to silence this."
- **Risk: `--dump-config` leaks secrets in CI logs.** Mitigation: redaction by suffix convention; document the limitation in `--help`. If the project has no secrets in config today, note that in `STATE.md` and move on.
- **Risk: TOML representation of edge values (None, nested dicts, datetimes) differs from JSON.** Mitigation: the migration script fails loudly on any JSON value it can't round-trip (e.g. `null` -> TOML has no null; either omit the key or use a sentinel). Decide per key during commit 3, document in the generated TOML's comments.
