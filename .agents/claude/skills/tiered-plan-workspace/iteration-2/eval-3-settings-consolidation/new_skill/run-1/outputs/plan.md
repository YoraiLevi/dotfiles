# Plan — Consolidate per-environment JSON config into a single TOML with sectioned environments

> Read top-down. Tier 1 is the manager's "should we do this?" — Tier 2 is the decider's "is the approach sound?" — Tier 3 is the reviewer's per-change dig-in — Tier 4 is the implementer's grounded step-by-step.

---

## Tier 1 — Objective & worthwhileness

- **Problem**: Configuration today is fragmented across `config/dev.json`, `config/staging.json`, `config/prod.json`. Shared values are duplicated three times, drift silently between files, and there is no single place to see "what differs between staging and prod." Adding a new key means editing three files and remembering to keep them aligned.
- **Why now**: Drift is already costing time — every new setting triggers a multi-file edit and an inevitable "we forgot to update prod" follow-up. No external blocker forces this now; the cost is recurring friction, not a single incident.
- **Success criteria**: A single `config/settings.toml` is the source of truth; loading `dev`/`staging`/`prod` returns values identical (semantically) to today's JSON files; old JSONs still load for one release with a visible deprecation warning; `myapp --dump-config <env>` emits the resolved merged config to stdout.
- **Risk surface**: Silent semantic drift during migration (a value translated wrong — e.g., null vs missing, int vs string) ships to prod undetected. Mitigation: golden-file diff between old-JSON-resolved and new-TOML-resolved for each environment before deleting JSONs.
- **Alternatives considered**: YAML (richer but whitespace-fragile and no stdlib parser pre-3.11 parity); a single JSON with environment keys (works, but no comments, no native section ergonomics — TOML wins on human-edit ergonomics for a config file).

---

## Tier 2 — Approach & shape

- **Approach**: Introduce a single `config/settings.toml` with a `[default]` table plus per-environment tables (`[dev]`, `[staging]`, `[prod]`) that override defaults. Build a `load_config(env)` that prefers TOML, falls back to the legacy per-env JSON with a `DeprecationWarning`, and a `--dump-config` CLI flag that prints the resolved dict.
- **Why this approach**: A `[default]` + override layering eliminates the three-way duplication that motivated the change; sectioned TOML keeps the file scannable and diff-friendly when only one environment's value changes.
- **Why not a flat JSON-with-env-keys**: It works but loses comments and forces the same overrides-vs-defaults pattern to be invented ad-hoc in JSON; TOML's section syntax expresses the same shape natively and is the documented Python config format since `tomllib` (3.11+).
- **Scope IN**:
  - New `config/settings.toml` with `[default]` + `[dev]` / `[staging]` / `[prod]` overrides.
  - One-shot migration script that reads existing JSONs, factors out shared keys into `[default]`, and writes TOML.
  - `load_config(env)` reader: TOML first, legacy JSON fallback with `DeprecationWarning`.
  - `--dump-config <env>` CLI flag emitting resolved merged config as JSON to stdout.
  - Unit tests covering: TOML-only path, JSON-only fallback path (warning emitted), TOML-wins-when-both-present path, dump-config output shape.
  - README/config docs updated to point at TOML as the source of truth.
- **Scope OUT**:
  - Removing the legacy JSON reader entirely — deferred to the release AFTER this one, tracked as a TODO comment in the loader plus an entry in `ROADMAP.md` (or equivalent).
  - Schema validation / typed config objects (e.g., pydantic) — out of scope; tracked as a follow-up note in the loader docstring.
  - Secrets handling / env-var interpolation — out of scope; current JSONs don't do this and adding it expands the blast radius.
  - Multi-file TOML (e.g., split overrides per environment) — explicitly rejected; the whole point is one file.
- **Delivery**: One PR, one commit (squash if iterative). Solo dev. New branch off `main`, e.g. `refactor/config-toml`.
- **Done when**: `pytest` green; `python -m myapp --dump-config prod` prints the same resolved dict (key-for-key) as `json.load(open('config/prod.json'))`; running with only the legacy JSONs present emits a `DeprecationWarning` and still works.

## Tier 3 — Per-change overview

### Change 1: New `config/settings.toml` with default + per-env tables

- File has four top-level tables: `[default]`, `[dev]`, `[staging]`, `[prod]`.
- `[default]` holds every key whose value is identical across all three current JSONs.
- Each `[<env>]` table holds ONLY the keys that differ from `[default]` for that environment.
- Comments at the top describe the layering rule ("env overrides default; missing keys inherit").
- Generated by the migration script (Change 3), not hand-authored, to guarantee semantic parity.
- **Why this matters for the objective**: The single-file layered structure is the whole point — it's what eliminates the three-way duplication that motivated the consolidation.

### Change 2: `load_config(env)` loader with TOML-first, JSON-fallback

- Function signature: `load_config(env: str) -> dict`.
- Resolution order: if `config/settings.toml` exists, parse it and merge `[default]` + `[<env>]`; else if `config/<env>.json` exists, load it and emit `DeprecationWarning` ("legacy per-env JSON config is deprecated; migrate to config/settings.toml — will be removed in the next release"); else raise `FileNotFoundError`.
- Uses `tomllib` (stdlib, Python 3.11+); if the project targets older Python, use `tomli` as a fallback import.
- Merge semantics: shallow merge — env table's keys overwrite default's keys; nested dicts are replaced wholesale, not deep-merged. (Document this; matches current JSON semantics where each file is standalone.)
- **Why this matters for the objective**: The one-release backwards-compat is explicit user-requested scope; without the fallback, every consumer would have to migrate in lock-step with this commit.

### Change 3: One-shot migration script

- Standalone script (e.g., `scripts/migrate_config_to_toml.py`) — not part of the runtime package.
- Reads all three JSONs, computes the set of keys whose values are identical across all three (deep-equal), promotes those to `[default]`, leaves the rest in their per-env tables.
- Writes `config/settings.toml` with stable key ordering (sorted) and a header comment.
- Run-once, idempotent (running it again produces the same file).
- **Why this matters for the objective**: Hand-translating three JSONs to TOML is the highest-risk step for silent drift; a script makes it mechanical and re-runnable if the JSONs change before the PR lands.

### Change 4: `--dump-config <env>` CLI flag

- Adds an argparse (or whatever the project uses) flag: `--dump-config ENV`.
- When set, calls `load_config(ENV)`, prints `json.dumps(cfg, indent=2, sort_keys=True)` to stdout, exits 0.
- Skips normal app startup — pure config-inspection mode.
- **Why this matters for the objective**: A dump command is the verification surface for "did the migration preserve semantics?" — it's what makes the golden-file diff in the risk-surface mitigation possible.

### Change 5: Tests covering all three loader paths + dump

- Test cases:
  - TOML present, JSON absent → TOML wins, no warning.
  - TOML absent, JSON present → JSON loads, `DeprecationWarning` emitted (assert via `pytest.warns`).
  - Both present → TOML wins, no warning (TOML is the new source of truth).
  - Neither present → `FileNotFoundError`.
  - `--dump-config prod` → stdout matches expected JSON for the prod env.
- Uses `tmp_path` fixture; does not touch the real `config/` directory.
- **Why this matters for the objective**: The fallback + warning behavior is the explicit user-requested contract; without tests it silently regresses the next time someone refactors the loader.

### Change 6: Docs update

- README config section (or `docs/config.md` if it exists) updated to describe the TOML format and the layering rule.
- One paragraph noting the legacy JSON fallback is temporary and will be removed in the next release.
- **Why this matters for the objective**: The whole point is single source of truth; if docs still point at JSON, the consolidation didn't really happen.

### Counts / scale anchor

- 3 legacy JSON files retired (kept on disk for one release).
- 1 new TOML file added.
- ~1 loader function + ~1 CLI flag + ~5 test cases + 1 migration script + 1 docs update — 5 code touchpoints, all in one commit.

### Honest debt

- Legacy JSON-reading branch in `load_config` is dead code by design — it exists only to emit the deprecation warning. Tracked via a `# TODO(next-release): remove legacy JSON fallback` comment at the branch.
- Shallow-merge semantics may surprise someone who expects nested-dict deep-merge; documented in the loader docstring and the TOML file's header comment rather than fixed (current JSONs don't deep-merge either, so this is parity, not a regression).

## Tier 4 — Implementer guide

### Step 1: Inventory current JSON keys and decide stdlib-vs-tomli for parsing

This step lands here because the migration script and loader both depend on knowing what's actually in the JSONs and which TOML parser is available — answering both unblocks every later step.

- Read `config/dev.json`, `config/staging.json`, `config/prod.json` and note the union of keys and which values are identical across all three.
- Check `pyproject.toml` (or `setup.py` / `setup.cfg`) for `python_requires`. If Python 3.11+, use `tomllib` (stdlib); otherwise add `tomli` to deps, because `tomllib` only landed in 3.11 and silently importing it on older Python would `ImportError` at runtime.
- Note whether the project already uses `argparse`, `click`, or `typer` for its CLI — the `--dump-config` flag wiring depends on this.

Checkpoint: Inventory written as scratch notes (not committed); parser choice and CLI framework identified.

### Step 2: Write the migration script and run it to generate `config/settings.toml`

This step lands here because generating the TOML mechanically (rather than hand-writing it) is the load-bearing risk mitigation for silent drift — running this first means every downstream step has the real TOML to test against.

- Create `scripts/migrate_config_to_toml.py`.
- Script logic:
  - Load all three JSONs into dicts.
  - Compute `default = {k: v for k, v in dev.items() if k in staging and k in prod and dev[k] == staging[k] == prod[k]}`, because keys with identical values across all three are the duplication we're consolidating.
  - For each env, compute `overrides = {k: v for k, v in env_dict.items() if k not in default or default[k] != v}`.
  - Write TOML using `tomli_w` (or hand-serialize if the project disallows new deps — TOML for flat scalar tables is mechanical to emit), with `[default]` first, then `[dev]`, `[staging]`, `[prod]` in that order; keys sorted within each table.
  - Prepend a header comment: `# Generated by scripts/migrate_config_to_toml.py. Edit by hand after migration.`
- Run the script once: `python scripts/migrate_config_to_toml.py`. Inspect the resulting `config/settings.toml` by eye against the JSONs.

Checkpoint: `config/settings.toml` exists; `diff <(python -c "import json; print(json.dumps({**default, **dev_overrides}, sort_keys=True))") <(cat config/dev.json | jq -S .)` (or equivalent) shows no semantic difference for each env.

### Step 3: Implement `load_config(env)` with TOML-first, JSON-fallback, deprecation warning

This step lands here because the loader is what every consumer of config will call — it has to land before the CLI flag (which uses it) and before the tests (which exercise it).

- Locate the existing config loader (search for `dev.json` / `staging.json` references, e.g. via `grep -rn 'dev.json' .`).
- Replace the loader body with:
  - Check `config/settings.toml` exists → open binary, `tomllib.load(f)`, return `{**data.get('default', {}), **data.get(env, {})}`.
  - Else check `config/<env>.json` → emit `warnings.warn("Legacy per-env JSON config is deprecated; migrate to config/settings.toml. Will be removed in the next release.", DeprecationWarning, stacklevel=2)` and return `json.load(f)`, because `stacklevel=2` points the warning at the caller, not at the loader internals.
  - Else `raise FileNotFoundError(f"No config found for env={env!r}")`.
- Add `# TODO(next-release): remove legacy JSON fallback` above the JSON branch, because the explicit one-release window is the user-requested contract and the comment is how we remember it next cycle.
- Update any cached `lru_cache` on the old loader to invalidate, if one exists — stale caches across a loader rewrite are a classic subtle bug.

Checkpoint: `python -c "from myapp.config import load_config; print(load_config('prod'))"` prints the resolved prod config.

### Step 4: Add `--dump-config <env>` CLI flag

This step lands here because the CLI flag depends on `load_config` from Step 3 and is what makes the Step 6 golden-file verification possible.

- In the project's CLI entrypoint (whatever Step 1 identified — argparse / click / typer), add a flag accepting an env name.
- When set, call `load_config(env)`, then `print(json.dumps(cfg, indent=2, sort_keys=True))`, then `sys.exit(0)` — bypass the rest of startup, because `--dump-config` is an inspection command, not an app run.
- If the project uses argparse: add `parser.add_argument('--dump-config', metavar='ENV')` and branch on `args.dump_config` before `main()` proper.

Checkpoint: `python -m myapp --dump-config prod` prints sorted JSON to stdout and exits 0.

### Step 5: Write tests for the four loader paths and the dump flag

This step lands here because the contract (TOML-wins, JSON-fallback-with-warning, dump-shape) is the user-requested behavior and is the regression surface a future refactor will most likely break.

- Create or extend `tests/test_config.py`.
- Use `tmp_path` and `monkeypatch.chdir(tmp_path)` so tests are isolated from the real `config/`.
- Cases:
  - `test_toml_only`: write a `config/settings.toml` with `[default]` + `[prod]`, no JSONs; assert `load_config('prod')` returns merged dict; assert no warnings via `warnings.catch_warnings(record=True)`.
  - `test_json_fallback_warns`: write only `config/prod.json`; assert `load_config('prod')` returns its content AND emits `DeprecationWarning`, using `pytest.warns(DeprecationWarning)`.
  - `test_toml_wins_over_json`: write both; assert TOML's values are returned; assert no warning, because once the TOML exists the user has migrated and shouldn't see deprecation noise.
  - `test_missing_raises`: neither file; assert `FileNotFoundError`.
  - `test_dump_config_cli`: invoke the CLI via `subprocess.run([sys.executable, '-m', 'myapp', '--dump-config', 'prod'], capture_output=True)`; assert exit 0 and stdout parses as JSON matching the expected dict.

Checkpoint: `pytest tests/test_config.py -v` — all five tests green.

### Step 6: Golden-file diff to prove semantic parity, then update docs

This step lands here because it's the verification gate before deleting (or rather, deprecating) the old JSONs — without this, the Tier 1 risk surface (silent semantic drift) is unmitigated. Docs land in the same step because they're a one-paragraph change and shouldn't justify their own commit.

- For each env in `dev`, `staging`, `prod`:
  - Run `python -m myapp --dump-config <env> > /tmp/new-<env>.json`.
  - Run `python -c "import json; print(json.dumps(json.load(open('config/<env>.json')), indent=2, sort_keys=True))" > /tmp/old-<env>.json`.
  - `diff /tmp/old-<env>.json /tmp/new-<env>.json` — must be empty.
- Update README (or `docs/config.md`) config section: describe the `[default]` + per-env layering, show a short example, note the legacy JSON fallback is temporary.
- Leave the legacy JSONs in place for the one-release deprecation window — do NOT delete them in this PR, because the whole point of the fallback is to give consumers a release to migrate.
- Add a `ROADMAP.md` (or equivalent) entry: `- Remove legacy per-env JSON config fallback (deprecated in vX.Y, remove in vX.Y+1)`.

Checkpoint: All three diffs are empty; README mentions TOML; ROADMAP has the cleanup entry.

### Step 7: Commit and open the PR

This step lands here because every prior step has a checkpoint that must pass before the diff is review-ready.

- Single commit on `refactor/config-toml` branch.
- Commit message: subject line names the consolidation, body summarizes the layering rule + the one-release fallback window.
- PR description points at the Tier 1 problem statement and links the three golden-file diff results as evidence.

Checkpoint: `pytest` green on the branch; PR open; CI green.

### Critical files (patterns repeat; representative paths only)

- `config/settings.toml` — new, generated.
- `config/dev.json`, `config/staging.json`, `config/prod.json` — kept; deprecated.
- `<package>/config.py` (or wherever `load_config` lives) — loader rewrite.
- `<package>/__main__.py` or `<package>/cli.py` — `--dump-config` flag wiring.
- `scripts/migrate_config_to_toml.py` — new migration script.
- `tests/test_config.py` — new/extended test module.
- `README.md` or `docs/config.md` — docs update.
- `ROADMAP.md` (or equivalent) — cleanup entry for the next release.

### Reusable utilities (referenced, not reinvented)

- `tomllib` (stdlib 3.11+) or `tomli` (back-port) — TOML parsing; do not write a hand-rolled parser.
- `tomli_w` — TOML writing in the migration script, if the project allows adding a dev-only dep; otherwise hand-emit (TOML for flat scalar tables is mechanical).
- `warnings.warn(..., DeprecationWarning, stacklevel=2)` — stdlib; do not invent a custom warning channel.
- `pytest.warns(DeprecationWarning)` — stdlib of pytest; do not assert via captured stderr.

### Hygiene constraints

- Use `git mv` if the loader file is renamed (e.g., `config_loader.py` → `config.py`); do not delete+create, because git history on the file is the easiest way to audit the loader's evolution.
- Commit message subject line: imperative, <= 72 chars, no AI co-author trailer.
- Do NOT delete the legacy JSONs in this PR — the one-release deprecation window is explicit user-requested scope; deleting them collapses the contract.
- Migration script is one-shot and goes under `scripts/`, not under the runtime package, because shipping a migration tool inside the package implies it's a supported runtime feature and it isn't.
- If `pyproject.toml` is touched (to add `tomli` or `tomli_w`), pin to a minor version, not exact — config tooling is stable and over-pinning creates resolver pain.
